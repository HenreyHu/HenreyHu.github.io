Overview

WAVES is a top-down stealth maze game built by a team of five in the first year of the programme, on AlphaEngine, a 2D C engine provided by DigiPen. The player throws rocks that emit light and sound waves, revealing the maze layout and luring enemies away, rather than seeing the whole level at once.

Role: Programmer. I built the game state architecture end to end, a shared state interface and a manager every screen in the game runs through, then implemented the screens on top of it, covering the menus, level select, three playable levels, and the pause, settings and exit overlays. I also built the shared interface layer used across all of them for button input, text rendering and font management. The wave mechanic, maze loading, player movement, and collision were built by teammates.

What I built

Game state architecture

Every screen in the game, splash, main menu, level select, instructions, the three levels, win, lose, credits, implements the same small interface, load, initialize, update, draw, free, unload. A single manager owns the active screen and tears down the previous one before switching, so state never leaks between screens. Screens do not call into the manager to switch themselves, instead they report what they want to transition to and the manager acts on it, which keeps the manager as the one place that decides when a transition actually happens.

Overlays

Pause, settings and exit are not separate states in the same sense as a level or a menu screen, they are overlays that sit on top of whatever level is currently running, gating input and drawing on top of it without tearing the level down and reloading it afterward. That distinction is what keeps pausing cheap, resuming just means the overlay stops drawing and releasing input, the level underneath was never unloaded in the first place.

Shared UI and font layer

Every screen's buttons run through the same hit testing code, which has to handle both world space, used during gameplay, and normalized screen space, used in menus, since a button placed in one space would test against the wrong region if checked with math meant for the other. Fonts are loaded once and cached by name rather than reloaded per screen, and the wall and boundary rendering for each maze uses a manually managed growable array rather than a fixed size buffer, so a maze layout is not capped at a size chosen ahead of time.

What I'd change

The state manager special cases the main menu state directly, using a cast to hand it a shared quit flag, rather than passing shared data to every state through the same interface. It worked for a project this size but every new state needing shared data would add another special case. The wall array also reallocates on every single wall added rather than growing in batches, which is quadratic over a full level load, a standard growable array with its size reserved up front from the maze dimensions would be both faster and simpler.

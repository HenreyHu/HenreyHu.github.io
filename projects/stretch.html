Overview

STRETCH is a 2D platformer built by a team of eight, six programmers and two artists, on a custom C++ engine written for this project. No Unity, no Unreal, the engine and its ECS were written by the team from the ground up. It was a stretch project, outside the normal coursework scope, taken on to work at a larger team size and on lower-level systems than earlier modules required.

Role: Programmer, AI & UI Champion. I built seven systems on top of the engine, enemy AI, the full persistence layer, checkpoint handling, the level editor's undo and redo system, the UI system, scene lifecycle, and the splash screen. The engine itself, the ECS core, and the top level game state machine were built by teammates.

What I built

Enemy AI

The enemy runs a four-state machine, Idle, Patrol, Spot, Charge. Detection checks the player's position against the enemy's facing direction and a detection range, so an enemy walked past from behind will not notice. The Charge attack times its warning effect off the actual animation frame the enemy is showing rather than a fixed timer, so the effect stays locked to the swipe no matter how fast or slow that particular charge animation plays.

Persistence layer

This is the largest system I own on the project. Every component type in the engine registers its own load and save function against a shared registry, so saving a level, saving a single entity, and saving a checkpoint all walk the same registry rather than three separate hand written paths. Entities also carry a lifetime category, level, persistent, or temporary, which decides what actually survives a level change versus what gets wiped along with it. The same per-entity JSON snapshot this system produces is what the level editor's undo system runs on, so the two never drift out of sync with each other.

Checkpoint system

Checkpoint interaction wires itself up automatically, creating one hidden observer entity the first time it runs rather than requiring a level designer to place a "game manager" object in every level. The actual save fires through the engine's message system, so the checkpoint code only needs to broadcast that a save should happen, not know how a save is written.

Editor undo and redo

Undo and redo works across every component type in the engine, not just transforms, by capturing a before and after JSON snapshot around an edit and comparing them, reusing the same snapshot format the persistence layer already produces. A transform drag gets its own lighter, dedicated path, since reserializing a whole entity on every frame of a gizmo drag would have been wasted work for something as small as a position change.

UI system

Menus, the health bar, and hit testing for every button and slider in the game. Buttons can live in either world space or normalized screen space depending on the menu, so hit testing runs two versions of the same rotated rectangle check depending on which space a given button uses. Controller navigation was added on top of the existing mouse driven menus afterward, reusing the same click and hover callbacks rather than rebuilding menu interaction around a controller first design.

What I'd change

Controller navigation grew on top of the mouse driven menus rather than being designed alongside them from the start, and the function that drives it shows that, it is long and carries several booleans a proper input mapping layer would replace. The editor's generic undo path snapshots and diffs an entity's full JSON on every edit, which is simple and correct but not cheap for entities with many components, a dirty flag system that only serialized what actually changed would scale better on larger scenes.
